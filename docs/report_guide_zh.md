# 上台報告小抄：先懂這些就能開始練習

## 三分鐘講稿

大家好，我的專題是「排球歷史賽事與球員數據管理系統」。這個專題用 MySQL 保存真實的德國排球聯賽資料，包含男子與女子聯賽，從 2013–2014 到 2018–2019，共六季。

資料來自 GitHub 的 volleystat 專案，原本是 R 套件資料。我用 Python 轉成 CSV，再進行清理，最後匯入 MySQL。資料庫包含 1,696 場比賽、6,330 局與超過三萬筆可識別的球員單場統計。

設計上，我把聯賽、賽季、球隊、球員、所屬關係、比賽、局數及球員統計拆成九張表。主鍵用來唯一識別一筆資料，外鍵用來連接不同資料表。例如 Match_Set 使用「比賽編號加局號」當複合主鍵，因為不同比賽都有第一局。

球員可能轉隊，所以我另外用 Player_Team_Season 保存每季所屬球隊，而不是直接在球員表放一個固定隊名。另一個重點是，來源的球員 ID 只在當季當隊有效，不能把球衣號碼當成全球球員 ID。我使用姓名、性別與生日做保守識別，無法確認的不同名字不直接合併。

這個系統可以回答五個問題：第一，某季各隊的勝率與排名；第二，同一球員跨季的表現；第三，兩隊過去交手的紀錄；第四，某季攻擊得分最多的球員；第五，五局大戰的比分和比例。例如男子 2018–2019 有 155 場比賽，其中 38 場打滿五局，比例是 24.52%。

資料清理時，我移除四筆完全重複的統計，另有 268 筆找不到名冊的統計被隔離保存，沒有補假球員。因此球員總分可能不完整，但比賽比分仍保留。匯入後我檢查了外鍵、局數、比分與統計，十項檢查都沒有發現違規；同一批資料重新匯入，也不會增加重複資料。

以上是我的專題，謝謝大家。

## 現場展示順序

1. 開英文企劃書，說明專題名稱與資料來源。
2. 開 ER 圖，只指三件事：Season_Team 連球隊與賽季、Player_Team_Season 保存轉隊、Match_Set 保存每局比分。
3. 在終端機執行 `python scripts/validate_data.py`，指出全部錯誤數為 0。
4. 執行 `python scripts/run_queries.py`，再開 `docs/query_results.md`。
5. 展示 Q1 勝率、Q2 跨季、Q5 五局比例。若時間足夠再介紹 Q3 與 Q4。

## 老師可能問的問題

**為什麼不用一張大表？** 會一直重複姓名與隊名，轉隊時容易覆蓋歷史，而且一場比賽會因球員人數被重複計算。

**PK 跟 FK 差在哪？** PK 是本表的唯一識別；FK 是參照別張表的有效編號。PK 像學號，FK 像選課紀錄裡填的學號。

**什麼是多對多？** 一支球隊可以參加很多季，一季也有很多隊。所以用 Season_Team 中間表拆成兩個一對多。

**同一球員換隊怎麼辦？** Player 仍是同一人；Player_Team_Season 新增不同隊伍或季別的關聯，舊紀錄保留。

**生日相同就是同一人嗎？** 不是，來源有同日出生的不同球員，還有雙胞胎，必須結合姓名與性別；不同拼字沒有證據不隨便合併。

**為什麼 match_id 要重新編號？** 上游比賽編號可能跨季重複。我們建立全域 ID，另外保存 source_match_id 供追溯。

**為什麼球員表不放 position？** 位置可能隨季或隊改變，因此放在 Player_Team_Season。

**攻擊成功率怎麼算？** 攻擊得分總和 ÷ 攻擊次數總和 ×100%，不是把每場百分比直接平均。

**五局比例怎麼算？** 該聯賽該季打滿五局場數 ÷ 該聯賽該季全部紀錄場數 ×100%。分母包含季後賽。

**有完全符合 3NF 嗎？** 核心表盡量正規化；統計表為了建立複合外鍵，保留 season_id 這項受約束冗餘，所以不宣稱全部嚴格符合 3NF。

**CHECK 能保證每場局數符合比分嗎？** 一般 CHECK 不能跨多列加總，所以程式在交易提交前會驗證，失敗就回滾。外鍵與單列 CHECK 由 MySQL 強制執行。

**資料可信嗎？** 使用公開真實來源，固定 Git commit，保留 RDA、CSV、來源文件與 SHA-256；這表示可追溯，不代表上游完全沒有錯誤。

**球員總分是完整生涯總分嗎？** 不是，是這六季來源裡可識別的單場紀錄總和，268 筆隔離統計未計入。

**重跑會發生什麼事？** 同一固定資料快照使用主鍵與 upsert 更新既有列，不會增加副本。它不是不同版本資料的自動刪除同步工具。
