期末專題企劃書 - Part I

專題名稱：排球歷史賽事與球員數據管理系統

Volleyball Historical Statistics Database System
課程：Database Systems

Part 1：專題介紹

1. 背景與目的

我們把德國排球聯賽六個歷史賽季的真實資料整理進 MySQL，方便查球隊勝率、球員歷年表現、歷史交手與五局大戰。資料來自 volleystat，不是自行編造。

資料含男女聯賽，2013–2014 到 2018–2019。實際匯入 2 個聯賽、12 個聯賽賽季、32 支球隊、940 個可解析球員身分、1,853 筆球員所屬球隊賽季、1,696 場比賽、6,330 局與 32,483 筆單場球員統計。

原始資料是 R 套件的 RDA，不是 CSV；我們用 Python 轉出 CSV。四筆完全重複統計去重，268 筆沒有對應名冊的統計隔離保存，沒有補假姓名。上游套件 DESCRIPTION 宣告 CC0。詳細來源、授權與缺值見 data_sources.md。

2. 五個有用的查詢

查詢 白話問題 使用方法 實際例子
Q1 球隊排名 這一季哪隊勝率最高？ 合併主客場、加總勝負、AVG 算勝率、DENSE_RANK 排名 男子 2018–2019，Haching 19 勝 3 敗，86.36%。
Q2 球員跨季表現 同一球員每季得分是否改變？ 球員 JOIN 統計與賽季，SUM 得分、攻擊、攔網與 Ace Robert Kromm 有五季紀錄；第一季 357 分，最後有紀錄的一季 259 分。
Q3 歷史交手 兩隊以前打過幾場、誰贏？ 同時找 A 主場與 B 主場，依日期排序 Berlin 與 Friedrichshafen 有 37 場交手。
Q4 最佳球員 哪位球員攻擊得分最多？ 每人加總，計算攻擊、攔網與 Ace 排名 男子 2018–2019，Sebastian Gevert 攻擊得分 399、Ace 47。
Q5 五局大戰 哪些比賽打滿五局？哪季最多？ 串接每局比分，計算五局場數除以總場數 全部 348 場；男子 2018–2019 為 38/155＝24.52%。

Q1 只看例行賽，依勝率與勝場排，並列共用名次，不是官方德甲積分榜。其他查詢看全部階段。球員統計因隔離紀錄可能不完整；沒有某季紀錄不代表該季得 0 分。Q4 的前十名是「攻擊得分前十」，同時附上各自在全部球員中的攔網、Ace 排名。

3. 為什麼要這樣設計 ER 圖？

聯賽底下有多個賽季；球隊可以參加多季，每季也有多隊，所以需要 Season_Team 中間表。球員可以換隊，不能在 Player 只放一個 team_id，所以用 Player_Team_Season 保留「誰、哪隊、哪季」。同一季有兩隊的紀錄也可以保存；來源沒有可靠的轉隊日期，不虛構起訖日。

一場比賽有主隊與客隊，並有三到五局。每局只保存一次，透過 match_id 連回比賽。球員單場統計另外存，避免把球員所有資料在每一場反覆複製。

球員原始 ID 是當季當隊的號碼，不能當全世界唯一 ID。我們以正規化姓名、性別與生日建立獨立 ID。名字不同但生日相同也不隨便合併，因為可能是不同人或雙胞胎；未確認的改名仍是限制。

Part 3：Database Schema（資料庫結構圖）

九張資料表的實際欄位、型別與主外鍵。結構已核對 MySQL 與 sql/schema.sql。

PK＝主鍵；FK＝外鍵；UK＝唯一約束。NULL 表示允許缺值。複合外鍵必須整組閱讀。下一頁起提供各表完整欄位、用途及主鍵選擇原因。

Part 3：Database Schema - 逐表說明

1. League

保存男子與女子聯賽。

完整欄位：league_id、league_name、country

Primary Key：(league_id)
選鍵原因：league_id 是穩定編號，不依賴可修改的名稱。

Foreign Keys：無。

2. Season

保存各聯賽的賽季。

完整欄位：season_id、league_id、source_season_id、season_name

Primary Key：(season_id)
選鍵原因：來源季別在男女聯賽重複，因此使用全域 season_id，並對 league_id＋source_season_id 設唯一約束。

Foreign Keys：

  • (league_id) → League(league_id)

3. Team

保存跨季球隊身分與最新顯示名稱。

完整欄位：team_id、team_name

Primary Key：(team_id)
選鍵原因：沿用來源跨季穩定 team_id，球隊贊助更名不會產生另一支球隊。

Foreign Keys：無。

Part 3：Database Schema - 逐表說明

4. Player

保存依來源解析的球員身分、姓名、性別與生日。

完整欄位：player_id、identity_key、player_name、gender、birthdate

Primary Key：(player_id)
選鍵原因：player_id 是獨立代理鍵；來源球衣號碼只在某季某隊有效，不能識別全球球員。

Foreign Keys：無。

5. Season_Team

保存球隊參與賽季與當季名稱，解決球隊與賽季的多對多關係。

完整欄位：season_id、team_id、season_team_name

Primary Key：(season_id + team_id)
選鍵原因：同一隊可參加多季，一季有多隊，所以 season_id＋team_id 合起來才唯一。

Foreign Keys：

  • (season_id) → Season(season_id)
  • (team_id) → Team(team_id)

6. Player_Team_Season

保存球員當季所屬球隊、來源編號、球衣與位置，保留轉隊歷史。

完整欄位：player_id、team_id、season_id、source_player_id、shirt_number、position

Primary Key：(player_id + team_id + season_id)
選鍵原因：player_id＋team_id＋season_id 識別一次季別名冊關聯，允許同一球員同季出現在不同隊。

Foreign Keys：

  • (player_id) → Player(player_id)
  • (season_id, team_id) → Season_Team(season_id, team_id)

Part 3：Database Schema - 逐表說明

7. Match

保存比賽日期、階段、主客隊與最終局勝負；時間為德國當地時間。

完整欄位：match_id、season_id、source_match_id、home_team_id、away_team_id、match_date、competition_stage、home_sets_won、away_sets_won

Primary Key：(match_id)
選鍵原因：來源比賽編號跨季可能重複，所以使用全域 match_id，同時保留 source_match_id。

Foreign Keys：

  • (season_id, home_team_id) → Season_Team(season_id, team_id)
  • (season_id, away_team_id) → Season_Team(season_id, team_id)

8. Match_Set

保存每場比賽依序排列的每局比分。

完整欄位：match_id、set_number、home_points、away_points

Primary Key：(match_id + set_number)
選鍵原因：每場都有第一局，所以必須用 match_id＋set_number 才能唯一識別一局。

Foreign Keys：

  • (match_id) → Match(match_id)

9. Player_Match_Stats

保存一名球員代表一隊在一場比賽中的攻擊、攔網及發球統計。

完整欄位：match_id、player_id、team_id、season_id、total_points、attacks、attack_points、blocks、aces、serve_errors、serves

Primary Key：(match_id + player_id + team_id)
選鍵原因：match_id＋player_id＋team_id 唯一識別球員代表該隊的單場紀錄。

Foreign Keys：

  • (match_id, season_id) → Match(match_id, season_id)
  • (player_id, team_id, season_id) → Player_Team_Season(player_id, team_id, season_id)

正規化、約束與實際驗證

核心設計盡量正規化。不過統計表的 season_id 可以由 match_id 得知，我們刻意保留它，讓兩組複合外鍵能保證「球員名冊賽季＝比賽賽季」。這是少量、受約束的冗餘，不能向老師說每張表都嚴格完全符合 3NF。

CHECK 限制主客不同、合法的 3 比幾結果、局號與非負統計；跨多列的規則，例如每場所有局加起來是否符合最終勝負，由匯入與驗證程式負責。實際在 MySQL 8.4.13 跑過，十項檢查全部為 0；同一資料重跑匯入，列數不增加。
